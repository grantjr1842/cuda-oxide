# cuda-oxide Roadmap

## Strategy Context
- v0.2.0 is ready to tag on `feat/sm75-baseline-support` (5 new commits ahead of `29a78ca`, total 11 ahead of main `15ac1b6`): SM75 is the compile/run default, sm75 gate extracted into a testable helper, target resolution split, cp.async + bar.warp.sync hardened as sm_80+, named-barrier `bar.sync` added as sm_80+, CI baseline job + doctor check, doc-honesty tests for the §3 error string, mir-lower TODO closures, and the supported-features detector-coverage table.
- The "guaranteed Turing-clean" claim in `sm75-support.md` §2.1 is now backed by the supported-features detector-coverage table (cuda-oxide-book/appendix/supported-features.md); the "No" rows are gone — every "No" is now "Yes (detector)" with a unit-test pin. The branch is ready for the 1.0 conversation when the user wants to start it.
- The single most expensive failure mode is still pliron upstream rev drift between the workspace and the excluded `rustc-codegen-cuda` crate (Cargo.toml L33-48) — any rev skew reintroduces duplicate-crate type-unification breakage. L1 is the long-term mitigation.
- Test-count hygiene: Phase A baseline + Phase C test work moved the workspace from 348 → 360 tests (+12). The "0 tests" claim for `cuda-device`, `cuda-host`, `dialect-mir`, and `dialect-nvvm` was wrong (they had 118, 39, 12, 4 tests respectively; the count was hidden by the Justfile `--lib --tests` recipe and the `cargo test --list` format difference). `fuzzer` and `cuda-bindings` are at 0 by design (FFI / experimental infra).

## OKRs
- **OKR1 — Earn the 1.0 conversation.** Graduate `rustc-codegen-cuda` from experimental to a documented semver-promised surface, backed by an end-to-end `async-mlp` example that runs in CI. KRs: (a) semver-promise doc published; (b) `async-mlp` e2e green in CI on the test GPU/PTX path; (c) one release tag cut after workspace test counts are honestly green.
- **OKR2 — Close the §2.1 detector table to "no unqualified NOs."** Every "No" row in `sm75-support.md` §2.1 is either (a) resolved to a detector with ≥2 unit tests, or (b) explicitly marked "intentionally not gated" with justification. KRs: (a) all rows resolved or justified; (b) the combined TMA/WGMMA/tcgen05 row split into per-feature rows that map 1:1 to detectors.
- **OKR3 — `cargo test --workspace` is the gate.** Every PR passes the full workspace test run, and no stable crate is silently at 0 tests. KRs: (a) `cargo test --workspace` green with honest counts (re-baselined from current ground truth); (b) every 0-test stable crate either has a follow-up initiative or an explicit "not unit-testable" justification.

## Risks & Dependencies
- **Risk:** pliron upstream rev drift between workspace and excluded `rustc-codegen-cuda` crate (Cargo.toml L33-48) reintroduces duplicate-crate type-unification breakage. **Mitigation:** L1 lockstep check + rev-bump procedure.
- **Risk:** `sm75-baseline.yml` first-run fragility (CUDA toolkit 13.1.1 + PTX-capable LLVM) could mask the gate regression we're trying to catch. **Mitigation:** N1 captures first-run notes; expect first-run failures and treat them as baseline, not regression.
- **Risk:** `cuda-host` is the runtime execution path for the §4 vecadd step and is at 0 tests — e2e could compile and fail at runtime with no test catching it. **Mitigation:** N4 flags cuda-host as a 0-test stable crate; X4 PTX-only smoke covers the build/runtime boundary; X3 closes the test gap.
- **Risk:** The d37c4d3 doc-honesty commit and e93c4dc CI baseline job are first-CI-run-validated in N1 — until then, the doc-honesty claim is not ground-truthed. **Mitigation:** N1 is the first item; do not pre-claim doc-honesty until N1 is green.
- **Risk:** Fuzzer corpus strategy (committed fixtures vs generated on the fly) is unresolved and affects Next-stage fuzzer CI time + reproducibility. **Mitigation:** X2 makes the call and records it.
- **Risk:** cp.async + bar.warp.sync are now sm_80+; users on the old permissive gate for sm_75 will hit new errors on upgrade. The doc-honesty test (N5) proves the gate fires, not that the error message is actionable. **Mitigation:** N5 asserts the §3 error string; v0.2.0 release notes (N6) call out the breaking change.
- **Dependency:** N6 (v0.2.0 cut) gates any 0.3.0 work and the 1.0 conversation in L4. **Owner:** release captain (TBD on N1 merge).
- **Dependency:** N1 (push + first CI) blocks the merge that makes N2–N6 mergeable. **Owner:** branch author.
- **Dependency:** X2 (fuzzer CI) depends on the X3 `cuda-device` / dialect-* work having established a baseline so fuzzer regressions in those crates are detectable. **Owner:** fuzzer owner (TBD on N1 merge).
